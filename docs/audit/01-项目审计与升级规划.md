# 企业采购与审批管理系统 — 第一阶段审计报告与升级规划

> 审计基线：`28ed0ff fix: align login query with mysql schema`
> 审计分支：`refactor-hardening`（从 `28ed0ff` 拉出）
> 审计方式：逐文件通读全部源码（后端 60 个 Java 文件、2 份 DDL、前端 8 个页面 + 6 个 JS 模块、Docker/Nginx 配置）
> 审计限制：本机未检测到 Maven、Docker（`mvn`/`docker` 不在 PATH），因此**本报告不含任何"测试通过""性能提升"结论**。凡标注 `[高置信·待实测]` 的，是读码可确定、但尚未在真实 MySQL 上执行验证的结论；第一阶段验收时会用一条 SQL 或一次接口调用确认。

## 0. 结论先行：最影响面试竞争力的 4 个真实问题

| # | 问题 | 一句话说明 | 为什么致命 |
|---|---|---|---|
| 1 | **项目里有两套后端，其中一套是内存假实现** | `service/ProcurementService.java` 把全部业务数据放在 `LinkedHashMap` 里，`controller/` 下的 `ApplicationController`、`OrderController`、`DashboardController`、`ProductController`、`UserController` 对外暴露 `/api/applications`、`/api/orders`、`/api/dashboard`、`/api/products`、`/api/users` | 面试官随手点 `/api/products` 只会看到 2 条硬编码商品，重启就丢。一旦发现，整套"MySQL + MyBatis-Plus"叙事全部作废 |
| 2 | **前后端契约没对上，UI 是靠 mock 撑起来的** | 前端 8 个页面里，创建申请、审批列表、订单列表、库存列表、调整库存、仪表盘、操作日志共 7 条链路调错接口或字段名不一致；`api/mock.js` 的数据形状才是页面真正期待的 | 这是"看起来完整、实际跑不通"的典型。面试时被要求"现场跑一遍"就穿帮 |
| 3 | **DDL 漂移导致同一份代码在两套环境表现不同** | `backend/src/main/resources/schema.sql` 与 `sql/procurement.sql` 是两份互相矛盾的表定义，谁先执行决定最终结构。Docker 环境下 `approval_record.result NOT NULL` 和 `purchase_order.creator_id NOT NULL` 都没有对应实体字段 | "审批"和"创建订单"两个核心写操作在 Docker 里会直接 500。这是最好的面试素材，但必须是被你主动讲出来的，而不是被面试官发现的 |
| 4 | **核心业务规则的校验是残缺的** | 可自审（审批人=申请人）、部门为 null 时审批任意部门、按 id 查任意申请无归属校验、`/api/auth/me` 回吐 BCrypt 密码哈希 | 权限与数据归属是 P0 面，任何一个都能让面试官把项目定级为"CRUD 练习" |

一句话总结：**这个项目的问题不是"技术不够高级"，而是"真实性和正确性不成立"。** 所以升级顺序必须是先让它"真"、再让它"深"。

### 1.2 两套实现对照

| 维度 | 内存版（controller/ + service/ProcurementService） | 数据库版（controller/v2 + business/PurchaseBusinessService） |
|---|---|---|
| 数据存储 | `LinkedHashMap<Long, X>` + `AtomicLong` 自增 | MySQL + MyBatis-Plus |
| 并发控制 | `synchronized` 方法（单机锁） | `UPDATE ... WHERE status=? AND version=?`（乐观锁 CAS） |
| 状态模型 | `Enums.OrderStatus{CREATED,RECEIVING,COMPLETED,CANCELLED}` | 字符串 `"CREATED" → "DELIVERED"` |
| 库存 | `Product.stock` 单字段 | `inventory_stock` + `inventory_transaction` |
| 事务 | 无 | `@Transactional` |
| 是否有调用方 | 前端 `/api/products`、`/api/users`、`/api/dashboard` 仍在用 | 前端主流程在用 |

**判断：内存版是历史遗留的"能跑起来的原型"，v2 是后补的真实实现，但 v1 没删、前端也没清理。** 改造规则第 1 条要求"保留核心业务、不推翻重写"——这里恰恰应该**删掉 v1、保留 v2**，因为 v1 不是"可复用代码"，而是"技术债务"。

### 1.3 核心业务链路（v2，真实实现）

```
POST /api/purchase-requests            createDraft()   status=DRAFT
POST /api/purchase-requests/{id}/submit  submit()      DRAFT→PENDING（CAS）
POST /api/approvals/{id}               approve()       PENDING→APPROVED/REJECTED + approval_record
POST /api/purchase-orders              createOrder()   APPROVED→PURCHASING + purchase_order(+item)
POST /api/purchase-orders/{id}/delivered  delivered()  CREATED→DELIVERED + inventory_stock 累加 + inventory_transaction
```

链路本身是合理的，**事务边界也基本正确**（每个业务动作一个 `@Transactional`，状态 CAS 与明细写入同事务）。这是项目里最值得保留、最容易讲出深度的地方。

## 5. 事务与并发风险专项

### 5.1 做得对的地方（面试要主动讲）

`submit / withdraw / approve / createOrder / delivered` 全部采用：

```sql
UPDATE purchase_request SET status=#{to}, version=version+1, updated_at=NOW()
WHERE id=#{id} AND status=#{from} AND version=#{version}
```

- 这是**乐观锁 + 状态机 CAS**的正确写法：`WHERE` 里同时锁定"期望的前置状态"和"读到的版本号"。
- 幂等的关键不在于加锁，而在于**第二次执行时 `affectedRows=0`**，业务层据此抛"状态已变更"，整个事务回滚。
- 第二次 `delivered` 不会重复加库存——因为它在 `transition` 处就被挡住了。**这一点是真本事，务必讲清楚。**

### 5.2 真实缺陷

| 缺陷 | 触发条件 | 后果 | 证据 |
|---|---|---|---|
| 首次建库存竞态 | 两个请求同时对同一 `productId` 首次入库 | 都读到 `null` → 都 `insert` → 第二个 `DuplicateKeyException` → 500 | `PurchaseBusinessService:22` |
| 重复商品明细 | 一个申请里同一个商品出现两次 | 第二条明细用首次读到的 `version` 更新 → `affectedRows=0` → "库存并发冲突" → 整单回滚。**这是纯 bug，跟并发无关** | 同上 |
| 无重试 | 任意一次 CAS 失败 | 直接 400，需要前端手动重试 | 同上 |
| 单号撞键 | 同毫秒并发创建 | `request_no`/`order_no` UNIQUE 冲突 → 500 | `:12`、`:21` |
| 幂等无兜底 | 状态机被绕过（如运维直接改库） | `inventory_transaction` 可能出现重复流水 | 无唯一约束 |

### 5.3 隔离级别与锁的适用场景（面试口径）

- 当前业务：`REPEATABLE READ`（MySQL 默认）+ 乐观锁 CAS 是合适的。理由：写冲突概率低、读多写少、避免长事务持锁。
- 什么时候该用悲观锁 `SELECT ... FOR UPDATE`：库存**扣减**（出库/领用）场景——先读后判断"够不够"，此时乐观锁会导致大量失败重试，改用 `UPDATE inventory_stock SET quantity=quantity-#{n} WHERE product_id=? AND quantity>=#{n}` 更好（把判断下推到 DB，天然原子）。
- 什么时候该升隔离级别：本项目不需要。`SERIALIZABLE` 会带来大量间隙锁，得不偿失。
- 这是 P1 阶段要补的"扣减"接口的真实落点——**不是为了秀技术，是因为"出库"这个业务本来就存在**。

## 6. 数据库设计风险专项

### 6.1 DDL 漂移（最高优先级）

项目里同时存在两份 DDL，且**互相矛盾**：

| 表 | `sql/procurement.sql`（Docker 初始化） | `backend/.../schema.sql`（应用启动初始化） | 冲突后果 |
|---|---|---|---|
| `sys_user` | `nickname NOT NULL`，无 `display_name`/`enabled`（后 ALTER 补 `display_name`） | 有 `display_name`、`enabled`、`department`，`nickname` 可空 | 实体只映射 `nickname`，靠 ALTER 兜住，勉强不炸 |
| `purchase_order` | 有 `creator_id BIGINT NOT NULL` | 无 `creator_id` | **Docker 下创建订单 500**（D-02） |
| `approval_record` | 有 `result VARCHAR(24) NOT NULL` | 只有 `action` | **Docker 下审批 500**（D-01） |
| `sys_operation_log` | 有 | **没有** | 本地非 Docker 下写日志报表不存在（D-16） |
| 库存 | `inventory` + `inventory_record` | 无（`inventory_stock` 只在 procurement.sql） | 本地非 Docker 下入库 500 |

执行顺序决定结果：Docker 里 MySQL 先跑 `01-procurement.sql`，`CREATE TABLE IF NOT EXISTS` 让 `schema.sql` 全部变成 no-op → 用严格版 DDL；本地直连空库时只有 `schema.sql` 生效 → 用宽松版 DDL。**同一份代码，两套表结构，两种行为。** 这是"环境不一致"的教科书案例，也是引入 Flyway 的最好理由。

### 6.2 索引设计

| 查询 | 现有索引 | 是否够用 | 建议 |
|---|---|---|---|
| `pending()`：`status='PENDING' AND department_id=?` | `idx_request_status(status)` | 不够：`status` 选择性极低（值域 6），单列索引会回表大量行 | `idx_status_dept(status, department_id)` |
| `byApplicant()`：`applicant_id=? ORDER BY created_at DESC` | `idx_request_applicant(applicant_id)` | 排序需 filesort | `idx_applicant_created(applicant_id, created_at)` |
| `orderList()`：`ORDER BY created_at DESC` 无过滤 | 无 | 全表 + filesort | `idx_order_created(created_at)` |
| `transactions().recent()`：全表 `ORDER BY created_at DESC` | `idx_inventory_tx_product(product_id)` | 完全不命中 | `idx_tx_created(created_at)` |
| `purchase_order.request_id`（校验是否已下单） | `idx_order_request(request_id)` | 够用，但建议加 UNIQUE | 改为 `UNIQUE uk_order_request(request_id)` |

> 注意：**当前数据量太小（演示数据 < 10 行），`EXPLAIN` 里 `type=ALL` 也可能只扫 3 行，看不出性能差异。** 所以索引优化必须配一个造数脚本（10 万行 `purchase_request`），否则"优化了"这个结论立不住。这一点在 P1 阶段会做成可复现的基准测试。

### 6.3 其他设计问题

- 无外键（除 `purchase_request_item`、`approval_record`、`purchase_order_item`），`purchase_order.request_id`、`inventory_transaction.product_id` 都是裸 id。
- `status` 用 `VARCHAR` 存枚举，无 `CHECK` 约束，且 `Enums` 类与实际写入的字符串不一致（`OrderStatus` 里没有 `DELIVERED`）。
- `purchase_request.department_id` 与 `sys_user.department_id` 冗余，无一致性保障（申请人调岗后历史单据的部门会与用户表漂移——这个其实是"快照"语义，是正确的，但代码里没有任何注释说明，容易被认为是错）。
- 金额全部 `DECIMAL(12,2)` / `DECIMAL(14,2)` 不统一；`total_amount` 由应用层累加计算后写回，没有 DB 层校验。

## 9. 最值得优先升级的 5 项（含面试价值、难度、验收标准）

### 升级 1：删除内存假实现，收敛为单一 DB 实现

- **面试价值**：★★★★★ —— 面试官第一句"数据存哪"就不会翻车；同时能讲"我如何识别并清理历史双实现"。
- **改造难度**：★★☆☆☆（删代码 + 补 3 个薄接口，但要注意 `Enums` 被 `AuthDtos` 引用）

### 升级 2：统一 DDL（Flyway 迁移）+ 修复阻断性写入失败

### P2 Redis 与性能 —— 只做一处，且必须选对目标

**结论：现在没有值得缓存的业务查询。** 审批列表、订单列表都是强实时 + 小数据量 + 写后即读，缓存只会带来一致性问题。

**唯一合理、且是真实热点的缓存目标：鉴权链路。** `JwtAuthenticationFilter` 每个请求执行 2 条 SQL（`catalog.user` + `catalog.roleCodes`），这是全站 QPS 的乘法器。做法：

- Key：`auth:roles:{userId}`，Value：角色集合，TTL 10 分钟；
- 失效：角色/权限变更时 `del`（`AdminService.saveRole/update` 已有 `evict` 雏形，但 key 名不对）；
- 穿透：用户不存在时缓存空值 `""`，TTL 60 秒；
- 击穿：TTL 加 ±10% 随机抖动（当前权限数据量小，不需要逻辑过期 + 互斥重建，过度设计）；
- 基准测试：`wrk`/`ab` 打 `/api/purchase-requests`，对比缓存前后 P99 与 QPS，并贴 `SHOW GLOBAL STATUS LIKE 'Com_select'` 差值证明 DB 查询次数下降。

> 这就是"不为用 Redis 而用 Redis"的正确姿势：**先证明有热点，再证明缓存有效。** 面试时明确说"我评估过业务列表缓存，收益为负，所以只缓存了鉴权"——这比"我用了 Redis 缓存所有列表"高一个段位。

### P3 测试/工程化/可观测 —— 全做

见升级 5。Swagger 用 `@Operation` + `@Schema` 补齐，并在 README 里给出"文档地址 + 一份 curl 示例"。

## 11. 高级技术逐项评估（不做，但要能答"为什么不做"）

| 技术 | 业务需求是否存在 | 引入成本 | 面试价值 | 结论与理由 |
|---|---|---|---|---|
| RabbitMQ / Kafka | 弱。唯一候选：入库后"通知申请人"、审批超时提醒 | 高（新增中间件 + 事务消息 + 幂等消费 + 运维） | ★★★☆☆ | **不做。** 当前是强同步的业务闭环，异步化的收益只有"响应快 50ms"，成本远大于收益。面试这样答："我用 `@TransactionalEventListener(AFTER_COMMIT)` 解耦通知，单体下够用；只有当出现跨系统、需削峰、需重放时才上 MQ。" |
| 定时任务 | 中。审批超时自动提醒、库存低于阈值预警 | 低（`@Scheduled` 即可） | ★★★☆☆ | **可做 1 个**（库存预警扫描），成本极低且业务合理；但必须先解决"多实例重复执行"，否则就是隐性 bug——这正好是引到分布式锁的天然话题。 |
| 分布式锁 | 当前**无需求**（单实例） | 中 | ★★★★☆ | **不引入 Redisson。** 但要在面试里讲清楚：什么时候必须用（多实例下定时任务、多实例下的"读-判断-写"）、为什么本项目不需要（DB 条件更新已足够）、Redis 锁的坑（超时续期、主从切换丢锁、误删他人锁）。 |

## 15. P2 阶段补充的实测结论（把推断变成证据）

| 结论 | 实测方式 | 实测结果 |
|---|---|---|
| `sql/procurement.sql` 在 MySQL 8 上不可执行 | 逐条执行脚本（隔离库 `procurement_verify`，3307） | `FAILED at statement #28: ALTER TABLE sys_user ADD COLUMN IF NOT EXISTS display_name ...` → `EXECUTED_OK=27 TOTAL=48` |
| 全新部署后表结构缺关键列 | 查 `information_schema.columns` | `purchase_request` 只有 id/request_no/applicant_id/department_id/total_amount/reason/status/apply_time/create_time/update_time —— **无 version / created_at / updated_at**；`purchase_order` 无 version，且 `creator_id` 存在；`approval_record` 只有 result，无 action |
| 补齐 DDL 后核心业务闭环真的是通的 | 补 22 条 ALTER/CREATE 后跑全流程 | 创建 DRAFT(11998) → 提交 PENDING → 审批 APPROVED → 下单 CREATED → 入库 DELIVERED；库存 `quantity=2, version=1`；流水恰好 1 条 |
| 乐观锁状态机确实能防重复 | 连续两次调用同一接口 | 第 2 次 submit → 400「申请状态已变更」；第 2 次 approve → 400；第 2 次 delivered → 400「订单已处理」，库存仍为 2、流水仍为 1 条 |
| `/auth/me` 泄漏密码哈希 | 登录后调 `/api/auth/me` | 响应体 **含 `password` 字段**（D-03 成立） |
| 审计日志操作人恒为空 | 调 `/api/admin/operation-logs` | `"operatorId": null`（D-11 成立） |
| 不存在的路由返回 500 而非 404 | 调已删除的 `/api/applications`、`/api/orders` | **HTTP 500**（`GlobalExceptionHandler` 的 `Exception` 兜底吞掉了 `NoResourceFoundException`）→ 补强 D-10 |
