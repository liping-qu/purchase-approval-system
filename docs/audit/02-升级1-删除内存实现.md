# 升级 1：删除内存假实现，收敛为单一 DB 实现

> 分支：`refactor-hardening`　基线：`28ed0ff`
> 状态：**代码完成；编译、打包、HTTP 端到端、重复请求拦截均已实测通过**

---

## 1. 这一步解决什么问题

审计报告 §0 第 1 条：项目里同时存在两套后端。

- `service/ProcurementService` 把用户、商品、供应商、申请、订单、库存全部放在 `LinkedHashMap` / `ArrayList` 里，
  用 `synchronized` 方法充当并发控制；
- 与之配套的 `controller/ApplicationController`、`OrderController`、`DashboardController`、
  `ProductController`、`UserController` 对外提供 `/api/applications`、`/api/orders`、`/api/dashboard`、
  `/api/products`、`/api/users`；
- 前端 `api/index.js` 里 `dashboard()`、`users()` 仍然打这套接口。

后果不是"代码冗余"，而是**项目叙事不成立**：面试官访问 `/api/products` 会拿到硬编码商品，
重启容器后新建的申请全部消失，"MySQL + MyBatis-Plus + 事务 + 乐观锁"这套说法会被一次点击推翻。

## 2. 方案与取舍

**选择：删除内存版，把仍在被前端使用的 3 个接口按 DB 版重写。**

不选"保留内存版作为演示数据源"的理由：

1. 演示数据应该来自 SQL 种子（`sql/procurement.sql` 已经在做这件事），不需要第二套代码；
2. 两套状态机（`Enums.OrderStatus` 与字符串 `"DELIVERED"`）已经产生语义冲突，保留只会继续分裂；
3. 内存版的 `synchronized` 会给面试官错误信号——它会让人以为"这个项目用方法锁解决并发"，
   而真实实现用的是 DB 乐观锁，两种讲法互相矛盾。

**范围边界**：本步只做"实现收敛"，不做字段契约修复、不做权限校验加固、不动 DDL。
因此改造后仍有 7 处前后端字段不一致（审计报告 D-17），那是下一阶段的任务，本文不掩盖。

### 3.3 重写（3 个 controller）

| 文件 | 改造前 | 改造后 |
|---|---|---|
| `controller/DashboardController` | `service.applications().size()` 等内存计数，键名 `applicationCount/pendingCount` | `DashboardService.summary()`，键名 `totalRequests/pendingRequests/...`，与 `Dashboard.vue` 对齐 |
| `controller/ProductController` | `service.products()` 返回 2 条硬编码商品 | `CatalogMapper.products()` 查询 `sys_product where active=1` |
| `controller/UserController` | `service.users()` 返回 3 条硬编码用户，**无任何权限注解** | `AdminService.userSummaries()` 查询 `sys_user`，并收敛为 `ADMIN` / `user:manage` 才能访问 |

### 3.4 修改（6 个文件）

| 文件 | 改动 |
|---|---|
| `persistence/mapper/CatalogMapper` | 新增 `products()`；顺手把单行压缩代码展开为可读格式（SQL 语义未变） |
| `persistence/mapper/SysUserMapper` | 新增 `listWithRoles()`：左连部门 + 子查询 `GROUP_CONCAT` 取角色，整页 1 条 SQL，避免 N+1 |
| `admin/dto/AdminDtos` | 新增 `UserSummaryVO(id, username, nickname, department, status, roles)`——不含密码、不含权限明细 |

| `frontend/src/api/index.js` | `/dashboard` → `/dashboard/summary`；`/operation-logs` → `/admin/operation-logs`（原路径后端不存在，必 404） |
| `frontend/src/views/Dashboard.vue` | 删除硬编码的 `3 / 12 / 8 / 28` 与 `78%`，改为真实统计；"库存预警"改为可真实计算的"零库存商品"；最近申请直接取 `summary.recent`，少发一次请求 |

## 4. 改造后的调用链

```
GET /api/dashboard/summary
  DashboardController.summary()
    → DashboardService.summary()
      → DashboardMapper.statusCounts()      SELECT status, COUNT(*) FROM purchase_request GROUP BY status
      → DashboardMapper.orderCount()        SELECT COUNT(*) FROM purchase_order
      → DashboardMapper.supplierCount()     SELECT COUNT(*) FROM sys_supplier WHERE active=1
      → DashboardMapper.productCount()      SELECT COUNT(*) FROM sys_product WHERE active=1
      → DashboardMapper.zeroStockCount()    SELECT COUNT(*) FROM inventory_stock WHERE quantity<=0
      → DashboardMapper.recentRequests()    purchase_request LEFT JOIN sys_user ORDER BY created_at DESC LIMIT 5

GET /api/products
  ProductController.list() → CatalogMapper.products() → sys_product

GET /api/users   [ADMIN / user:manage]
  UserController.list() → AdminService.userSummaries() → SysUserMapper.listWithRoles()
                          → sys_user LEFT JOIN sys_department + 子查询 sys_user_role/sys_role
```

3. 原有的乐观锁状态机是有效的——重复入库后库存仍是 2、流水仍是 1 条，第二次请求得到 400 而不是二次累加。
